Una base transaccional no falla por ‘ser chica’: falla por la carga equivocada

  • Millones de eventos por minuto: escritura y lectura compiten con reportes.
  • Datos que no son filas: JSON variable, logs, imágenes, audio, PDF.
  • Histórico de años: el reporte recorre todo y bloquea la operación.
  • Costo: escalar la base para analítica encarece la transacción.
  • Gobierno: no todos los datos tienen la misma sensibilidad ni retención.
P.E. Data Engineer · Azure · M3S03 · 4/31

Big Data no es ‘muchos datos’: es un conjunto que no cabe en el enfoque anterior★

  • Volumen: la escala supera lo que una máquina o una base tradicional manejan con comodidad.
  • Velocidad: los datos llegan y cambian rápido; la decisión tiene ventana.
  • Variedad: filas, JSON, texto, imágenes, audio, logs y eventos.
  • Veracidad/valor: más datos no significa datos confiables ni útiles.
  • La definición importa menos que la decisión: qué guardas, dónde y para qué.

El ciclo de vida del dato: cuatro fases que se diseñan juntas★★

El ciclo no es una línea recta: la exploración descubre datos faltantes y vuelve a la ingesta. La arquitectura debe permitir ese regreso sin romper el histórico.

P.E. Data Engineer · Azure · M3S03 · 7/31

Batch y streaming no son ‘viejo’ y ‘nuevo’: son ventanas de decisión★

Batch

  • Procesa bloques por horario o tamaño.
  • Ejemplo: cierre diario de ventas y conciliación.
  • Más simple de operar y de reprocesar.
  • La decisión espera; el costo suele ser menor.

Streaming

  • Procesa eventos a medida que llegan.
  • Ejemplo: stock, fraude, clics o alertas.
  • Ventana corta; exige manejo de atrasos y duplicados.
  • Más complejo y sensible al costo por evento.

Por qué una consulta de dos columnas no necesita leer todas las columnas★★

No es que un formato sea universalmente mejor: es que la consulta analítica lee pocas columnas de muchas filas. Para una escritura transaccional puntual, el cálculo cambia.

P.E. Data Engineer · Azure · M3S03 · 11/31

Data Warehouse: verdad curada para decidir★

Fortalezas

  • Esquema definido y modelado para BI.
  • Consultas SQL maduras y gobierno fuerte.
  • Calidad y conformidad entre áreas.
  • Ideal para métricas estables y reportes.

Límites

  • Caro para datos crudos y volúmenes enormes.
  • Rígido para esquemas que cambian por evento.
  • No es el mejor lugar para PDFs, audio o logs.
  • Cambiar el modelo puede exigir migraciones.
P.E. Data Engineer · Azure · M3S03 · 12/31

Data Lake: guarda primero, interpreta después★★

Fortalezas

  • Acepta cualquier formato y volumen.
  • Almacenamiento económico y elástico.
  • Sirve para datos crudos, históricos y ML.
  • No exige un esquema único al escribir.

Riesgos

  • Sin gobierno se convierte en un pantano.
  • Calidad y linaje no aparecen solos.
  • Consultas SQL menos eficientes sin formato y particiones.
  • Duplicados y archivos huérfanos se acumulan.
P.E. Data Engineer · Azure · M3S03 · 13/31

Lakehouse: la flexibilidad del lago con la confianza del warehouse★★

Qué agrega

  • Transacciones y esquema sobre archivos del lago.
  • Delta Lake: historial, ACID y evolución.
  • Una sola plataforma para BI, datos y ML.
  • Separación entre almacenamiento y cómputo.

Qué exige

  • Gobierno y catálogo desde el inicio.
  • Disciplina de zonas y calidad.
  • Motores compatibles con tablas Delta.
  • Control de costo de cómputo y pequeños archivos.

Delta Lake: qué agrega exactamente sobre Parquet★

  • Transacciones ACID: una escritura se confirma completa o no se confirma.
  • Historial de versiones: puedes leer una versión anterior y auditar cambios.
  • Esquema evolutivo controlado: agregar columnas sin romper lectores.
  • MERGE y upserts: actualizar sin reescribir todo el lago a mano.
  • Time travel: reproducir un reporte con el estado de ayer.

Spark y Databricks: cómputo distribuido, no una base más★★

  • Spark reparte el procesamiento en varios nodos y trabaja sobre archivos.
  • Databricks administra clusters, notebooks, jobs y tablas Delta.
  • No reemplaza a SQL: lo usa para transformar y consultar a escala.
  • El costo depende del clúster encendido, no solo del dato guardado.
  • Un job mal particionado puede ser más caro que un buen SQL.

adls://andina/gold/ventas_por_dia/
  anio=2026/mes=10/dia=10/
    parte-0001.parquet
  • La partición correcta coincide con el filtro frecuente.
  • Muchas carpetas pequeñas cuestan más que un archivo grande.
  • Particiona por fecha de negocio o carga, no por un campo con 3 valores.

Cinco preguntas de salida

¿Cuál es la diferencia entre un data lake y un lakehouse?

El lakehouse agrega transacciones, esquema e historial sobre archivos del lago, normalmente con Delta Lake.

¿Cuándo elegirías batch en lugar de streaming?

Cuando la decisión tolera esperar y el reproceso por lote es más simple y barato.

¿Por qué Parquet puede leer menos datos que un CSV?

Porque guarda por columnas y la consulta solo lee las columnas que necesita.

¿Qué debe tener una zona oro?

Una pregunta de negocio, un dueño, una regla de calidad y un consumidor claro.

¿Qué control falta si todos pueden leer bronce?

Clasificación, ACL/RBAC, minimización de PII y linaje; bronce no es público.
